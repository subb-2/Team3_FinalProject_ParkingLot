# MAIN_README — 프로젝트 전역 규칙

Jetson Orin Nano 기반 주차 관리/안내 시스템의 **전역 약속**을 모아둔 문서.

- 여기에는 **여러 모듈에 걸치는 규칙**만 적는다. (좌표계, 기둥 보정, 네이밍, 책임 경계)
- 특정 모듈에서만 쓰는 값은 여기 적지 말고 **그 모듈 상단 `CONFIG`**에 둔다.
- 규칙을 바꾸면 이 문서를 **먼저** 고치고 코드를 고친다. 문서와 코드가 다르면 코드가 틀린 것으로 본다.

---

## 1. 모듈 구조와 책임 경계

파일명 접두어가 곧 실행 순서이자 계층이다.

| 접두어 | 계층 | 모듈 | 책임 |
|---|---|---|---|
| **A** | 외부 연동 / 데이터 | `A00_uart_rx` | Zybo(FPGA)에서 Wi-Fi(TCP)로 차량번호 수신 |
| | | `A01_parking_manager` | 빈자리 배정, 입/출차 처리, 오주차 자리 정정 |
| | | `fee_calculator` | 주차 시간 기반 요금 계산 |
| **B** | 비전 | `B00_camera_input` | 카메라 열기 (Windows 웹캠 / Jetson GStreamer 자동 분기) |
| | | `B01_car_detection` | YOLO 차량 검출 |
| | | `B02_car_mot` | MOT 추적(OC-SORT) + 차량번호 매칭 (단일 활성 차량 + 재바인딩) |
| | | `B03_map_setting` | 기둥 보정 화면(`/calibrate`)과 좌표 저장 |
| | | `B_main` | B00 → B01 → B02 통합 실행 |
| **C** | 위치/경로 | `C00_navigation` | 기둥 보정 기반 픽셀↔실좌표 변환, 진행방향 추정, 안내 판정 |
| | | `C01_path_planner` | 경로 계산 (A* + 일방통행), 카메라를 쓰지 않음 |
| | | `C02_lot_layout` | 격자(`map_data`) → 실좌표(cm) 변환. 기둥·자리·입출구 좌표 생성 |
| | | `C_main` | B + C 통합 실행 |
| **D** | 표시 | `D00_ui_navi` | 조감도 맵 UI, 차량 시점 내비 화면 |
| | | `D_main` | B + C + D 통합 실행. 카메라/내비/조감도 3화면 (개발용) |
| **E** | 최종 | `E00_final_ui` | 관제 화면(네 구간), 주차 완료/오주차 판정 |
| | | `E_main_final` | **최종 진입점.** A(수신) → B(카메라·MOT) → C → E 순차 실행 |

**의존 방향은 항상 아래로만.** `C00 → C01 → C02 → data/map_data` 순이며 역방향은 금지.

각 모듈은 **자기 책임만** 한다. 예: B02는 YOLO를 들고 있지 않고 검출 결과를 인자로 받는다.

## 2. 좌표계 규칙

프로젝트에 좌표계가 3개 있다. 변수 이름으로 구분한다.

| 이름 | 단위 | 원점 / 방향 | 쓰는 곳 | 변수명 |
|---|---|---|---|---|
| **이미지 좌표** | px | 화면 좌상단 (0,0), y 아래 + | B01, B02 | `image_pos`, `center`, `bbox` |
| **실좌표 (world)** | **cm** | **기둥 1번(왼쪽 위) = (0,0)**, x 오른쪽 +, **y 아래 +** | C00, C01, D00 | `world_pos`, `*_world`, `*_cm` |
| **격자 좌표** | 칸 | `map_data.grid_map` 기준 | `map_data`, `C02`, `C01` | `cell`, `(row, col)` |

규칙:

- **모듈 경계를 넘는 위치 정보는 반드시 실좌표(cm)** 로 주고받는다. 이미지 좌표는 B 계층 밖으로 나가지 않는다.
- 변환은 `PillarMapper.pixel_to_cm()` / `cm_to_pixel()` 만 사용한다. 직접 호모그래피를 곱하지 않는다.
- **y축이 아래로 증가**한다. 각도 계산 시 `atan2(dy, dx)`의 양수 방향이 **시계 방향**이다.
  → 각도 차이가 양수면 **우회전**이다. (`C00._compute_guide` 참고)
- 입출구는 `GATE1_WORLD_POS`(입구, 모든 경로의 출발점)와 `GATE2_WORLD_POS`(출구)로 나뉜다.
  둘 다 `C02_lot_layout`이 격자에서 만든다.

## 2.1 일방통행

주차장 통로는 **한 방향으로만 돈다.** 화면 기준(위가 row 0, 왼쪽이 col 0)으로 **반시계 방향**이다.

```
입구(row 8, col 8)
  → 아랫줄을 오른쪽으로
  → 오른쪽 통로를 위로     D-4 → D-3 → D-2 → D-1
  → 윗줄을 왼쪽으로
  → 왼쪽 통로를 아래로     A-1 → A-2 → A-3 → A-4
  → 아랫줄을 오른쪽으로 → 출구(row 8, col 3)
```

정의는 **`data/map_data.py`의 `ONE_WAY_LOOP` 한 곳**에 있다. 순환 차선의 중심선을 이루는
모서리 칸을 **주행 순서대로** 적은 목록이고, 마지막 칸에서 첫 칸으로 닫힌다.
방향을 뒤집으려면 목록 순서만 뒤집는다. 차선을 옮기려면 칸 번호만 고친다.

| 단계 | 모듈 | 하는 일 |
|---|---|---|
| 정의 | `data/map_data.ONE_WAY_LOOP` | 격자 칸으로 순환선을 적는다 + 통로 위인지 검증 |
| 변환 | `C02_lot_layout.ONE_WAY_SEGMENTS_WORLD` | 실좌표(cm) 선분으로 바꾼다 |
| 적용 | `C01_path_planner.OneWayField` | 격자 칸마다 통행 방향을 만들고 A\*에 역주행 벌점을 물린다 |
| 표시 | `D00`(조감도) | 바닥 화살표로 그린다. 2·3번 구간에는 그리지 않는다 (7절) |

판정 규칙 — 어떤 지점의 통행 방향은 **가장 가까운 순환선 구간의 방향**이다.
그 방향과 가려는 방향의 cos으로 본다.

| cos | 뜻 | 처리 |
|---|---|---|
| > 0 | 순방향 | 그대로 |
| ≈ 0 | 옆으로 빠짐 (자리 진입, 차선 변경, 중앙 섬 접근) | **그대로** |
| < 0 | 역주행 | 한 칸마다 `WRONG_WAY_PENALTY_CM` 벌점 |

**수직 이동을 막으면 안 된다.** 막으면 중앙 섬(B/C열)에 아예 들어갈 수 없다.

벌점은 배수가 아니라 **한 칸당 정액**이다. 배수로 두면 짧은 역주행이 싸져서
'자리를 조금 지나쳤을 때 살짝 후진하는' 경로가 나온다. 정액이면 한 칸만 거꾸로 가도
이미 한 바퀴 도는 것보다 비싸다. 값은 주차장 둘레(약 480cm)보다 크게 잡는다.

`None`으로 두면 역주행을 아예 막지만 **권장하지 않는다.** 조건이 하나라도 어긋나면
경로가 안 나와 안내가 통째로 멈춘다. 시연 중에 화면이 비는 것이 가장 나쁘다.

### 차선 따라가기 (역주행 벌점만으로는 부족하다)

위 표의 **cos ≈ 0을 그대로 두는 것**이 구멍이었다. 이 주차장은 가운데가 통째로 빈
도로라, 흐름에 수직으로 가로지른 뒤 방향이 같은 곳에서 올라가는 길이 늘 더 짧다.
그래서 입구 → A-2가 D열 통로(col 11)를 타지 않고 **주차장 한복판(col 8)을 곧장
질러 올라갔다.** 판정상 역주행은 아니지만, 바닥 화살표는 순환 차선 위에만 붙어 있어서
눈에는 화살표를 무시하는 것으로 보이고 실제로 그 자리에서 맞은편 차와 마주친다.

그래서 **차선에서 벗어난 거리에 비례하는 비용**을 한 칸마다 얹는다. 벌점이 아니라
인력이라 값이 늘 0 이상이고, 휴리스틱(직선거리)이 그대로 하한이라 A\*의 전제가 유지된다.

| 설정 | 뜻 |
|---|---|
| `LANE_PULL_PER_CM` | 차선에서 1cm 벗어날 때마다 얹을 비용. 0이면 예전 동작(가로지르기) |
| `LANE_FREE_CM` | 차선 폭. 이 안은 벗어난 것으로 치지 않는다 |
| `LANE_SHORTCUT_TOLERANCE_CM` | 경로 단순화가 지름길을 낼 때 봐줄 비용 차이 |

**경로 단순화도 같이 고쳐야 한다.** 단순화는 두 경유점을 직선으로 잇는데, 그 직선이
차선 안쪽으로 부풀면 방금 차선을 따라 돌게 만든 경로가 다시 가로지르는 선으로 펴진다.
그래서 `_can_shortcut`은 **원래 구간보다 비싸지지 않는 지름길만** 쓴다. 단순화는 격자의
계단 모양을 없애려는 것이지 더 싼 길을 찾는 것이 아니다.

### 가로/세로로만 안내한다

A\*의 이동 방향에서 **대각선을 뺐다.** 4방향만 쓴다.

대각선을 넣으면 통로를 비스듬히 가로지르는 경로가 나온다. 계산상으로는 그쪽이 짧지만
실제로 사람이 그렇게 몰지 않고, 화면에 그려지는 선도 어디서 꺾으라는 것인지 읽히지 않는다.
4방향이면 가로/세로 구간만 남아 **"직진 후 좌회전"** 형태로 떨어진다.

두 곳이 함께 따라와야 한다. `MOVES`만 고치면 어느 한쪽이 대각선을 되살린다.

| 곳 | 이유 |
|---|---|
| `_astar`의 휴리스틱 | 4방향에서는 **맨해튼 거리**가 정확한 하한이다. 직선거리를 쓰면 하한이 느슨해져 탐색이 몇 배로 늘어난다 |
| `_can_shortcut` | 단순화가 계단을 편다면서 대각선 구간을 만들면 대각선을 없앤 의미가 사라진다 |

`HAS_DIAGONAL`이 `MOVES`를 보고 자동으로 정해지므로, 되살릴 때는 `MOVES`만 고치면 된다.

경로는 맨해튼이라 조금 길어진다. (입구 → A-2 : 262cm → 292cm) 대신 계획은 3배 빨라졌다.
(최악 165ms → 51ms. 맨해튼 휴리스틱이 정확해진 덕이다)

확인 방법 — 카메라 없이 `python logic/C01_path_planner.py`. 자리마다 통행 방향을 찍고,
입구에서 D-4 / C-2 / A-1 / A-4로 가는 경로에 역주행 구간이 있는지 검사한다.
**A-4는 입구 바로 옆인데도 한 바퀴 돌아야 정상**이다 (아랫줄이 오른쪽으로만 가므로).
입구 → A-2가 292cm(한 바퀴)면 정상이고, 197cm면 가운데를 가로지른 것이다.

화면에서 확인하려면 **3번 구간**을 본다. 4번이 안내하는 것과 같은 경로가 격자 위에
파란 선으로 깔린다. 계획기가 역주행 구간을 물고 나오면 그 선이 **붉게** 그려지고
터미널에도 경고가 한 줄 남는다 (`C00._check_one_way`).

화살표를 눈으로 대조하고 싶으면 `C_main.CONFIG['DRAW_ONE_WAY_ARROWS']`를 True로 두면
2번 CCTV 영상에 겹쳐 그려진다. 평소에는 목업 바닥의 실물 화살표로 충분하다.

## 3. 기둥 보정 규칙

> 예전에는 기둥에 ArUco 마커를 붙이고 카메라가 자동으로 읽었다. 지금은
> **사람이 `/calibrate` 화면에서 기둥을 순서대로 클릭한다.** 마커 검출 코드는
> 걷어냈고, `PILL_MARKER_ID`의 번호는 '몇 번째로 찍을 기둥인가'라는 뜻으로 남았다.

### 3.1 기준점은 "기둥"이다. 자리가 아니다

> **기준점 1개 = 기둥 1개.** 주차 자리의 좌표는 **같은 열에 있는 기둥 두 개 사이를
> 행 위치만큼 보간**해서 계산한다.

`data/map_data.py`의 `grid_map`이 배치를 정의하고, `PILL_MARKER_ID`가 각 기둥 칸에 몇 번을 매길지 적어둔다. 실제 계산은 `C02_lot_layout.build_spot_world_pos()`가 한다.

이 규칙의 이점:

- **차량이 기준점을 가리지 않는다.** 자리 중앙을 기준으로 삼으면 주차하는 순간 그 자리가 차에 덮여 좌표 기준이 사라진다.
- **기둥이 반듯하게 놓이지 않아도 된다.** 각 기둥의 실좌표만 맞으면 자리 좌표가 따라서 맞는다.

> **배치 제약: 주차 구역이 있는 열에는 기둥이 최소 2개 있어야 한다.**
> 기둥 사이에 자리가 몇 칸 들어가든 상관없고(현재 2칸씩), 마지막 기둥 바깥의
> 자리는 외삽으로 처리된다. `C02_lot_layout.validate_layout()`이 이를 검사한다.

### 3.2 기둥은 동시에 "좌표계 기준점"이다

같은 기둥이 두 가지 역할을 겸한다.

1. **변환 기준점** — 4개 이상 찍으면 `findHomography`로 픽셀↔cm 변환을 만든다.
2. **자리 좌표의 근거** — 위 3.1.

그래서 **기둥을 하나라도 옮기면 두 가지가 동시에 영향을 받는다.**

### 3.3 기둥을 재배치하면 반드시 같이 고칠 것

| 위치 | 내용 |
|---|---|
| `data/map_data.py` → `grid_map` | 기둥/자리/도로 배치 (설계도) |
| `data/map_data.py` → `PILL_MARKER_ID` | 격자의 기둥 칸 → 클릭 순서. 이 표는 자동 생성이 불가능하다 |
| `C02_lot_layout.CONFIG` | 격자 한 칸의 실제 크기 (cm) |

**주의**: 기둥 번호와 좌표의 대응이 실제 배치와 어긋나도 오차는 작게 나온다(자기 자신과는 일관되므로). 오차만 보고 "맞다"고 판단하지 말 것. 화면에서 좌우가 뒤집혀 보이면 이 표가 틀린 것이다.

### 3.3-1 화면 방향

카메라가 주차장을 **입출구 반대편에서** 보고 있어서, 화면에 입구가 위쪽에 오고 좌우도
설계 배치와 반대로 잡힌다. `B00_camera_input.FRAME_ORIENTATION`으로 **카메라에서
읽자마자 한 번** 돌릴 수 있다. **현재 값은 `None`(돌리지 않음)이다.**

| 값 | 뜻 |
|---|---|
| `None` | 그대로 **(현재)** |
| `"180"` | 180도 회전. 위아래 + 좌우가 함께 뒤집힌다 |
| `"v"` / `"h"` | 위아래만 / 좌우만. **거울상이 되므로 권장하지 않는다** |

한 번 `"180"`으로 뒀다가 되돌렸다. 돌려서 맞추려면 기둥 보정을 다시 찍어야 하는데
그만한 값어치는 없었다. 위치 확인은 설계 방향으로 서 있는 3번 격자에서 하면 된다.

다시 돌릴 일이 생기면 `"v"`가 아니라 `"180"`을 쓸 것. 위아래만 뒤집으면 거울상이 되어
바닥 화살표와 글자가 반대로 보인다. 카메라를 반대편으로 옮겨 단 것과 같은 결과를
내려면 180도 회전이라야 좌우까지 맞는다.

**돌리는 곳은 반드시 한 곳이어야 한다.** 검출·추적·보정 클릭·화면이 전부 같은 프레임을
봐야 좌표가 어긋나지 않는다. 화면에 그릴 때만 돌리면 보정에서 찍은 좌표와 검출 좌표가
서로 뒤집힌 상태가 된다.

> **이 값을 바꾸면 저장된 기둥 보정은 못 쓴다.** 해상도는 그대로라 3.4의 해상도 검사에
> 걸리지 않으므로, 보정 파일에 방향도 함께 적고 `_load_saved_calibration`이 대조한다.
> 다르면 거부하고 `/calibrate`로 보낸다.

### 3.4 보정 절차

| 순서 | 하는 일 |
|---|---|
| 1 | `/calibrate`에서 기둥 10개를 표에 적힌 순서대로 클릭 |
| 2 | 4개 이상 모이면 `findHomography(RANSAC)`로 픽셀↔cm 변환 생성 |
| 3 | 자리와 입출구의 픽셀 좌표를 같은 열 기둥 사이 보간으로 채움 |
| 4 | `config/pillar_pixels.json`에 **해상도·화면 방향과 함께** 저장 |

> **저장된 보정이 있으면 첫 화면이 `/calibrate`로 넘어가지 않는다.** 이게 정상 동작인데,
> 기둥을 찍은 적이 없다고 생각하면 "보정이 실행되지 않는다"로 보인다. 시작 로그에
> `[INFO] 저장된 기둥 보정을 불러왔습니다`가 있으면 그 경우다.
> 다시 찍으려면 2번 구간 왼쪽 아래 **[기둥 보정]** 버튼(`/calibrate`)을 쓴다.
> 좌표계가 아직 없으면 이 버튼이 붉게 **[기둥 보정 필요]** 로 바뀐다.

기둥의 설계 좌표(`MARKER_WORLD_POS`)는 실측하지 않는다. `C02_lot_layout.uniform_marker_world_pos()`가 격자와 `CELL_W/H_CM`에서 자동 생성한다. 사람이 대는 것은 화면 위의 픽셀 위치뿐이다.

> **저장된 보정은 같은 해상도일 때만 재사용한다.** 좌표가 이미지 픽셀이라
> 해상도가 달라지면 전부 어긋나는데, 화면은 멀쩡해 보이고 자리만 조용히 밀린다.
> `C_main._load_saved_calibration`이 해상도를 대조해 다르면 거부한다.
> 다시 찍으려면 `/calibrate`, 저장된 것을 지우려면 `/recalibrate`.

### 3.5 현재 배치

```
격자 9행 x 13열, 기둥 10개(1~10), 주차 자리 12개

      c0   c1 c2  c3  c4   c5   c6  c7   c8  c9 c10 c11  c12
  r0  O1    .  .   .   .    .    .   .    .   .   .   .   O8     O숫자 = 기둥(클릭 순서)
  r1  A-1   .  .   .   .    .    .   .    .   .   .   .   D-1    .     = 도로
  r2  A-2   .  .   .   .   O4    .  O6    .   .   .   .   D-2    IN/OU = 입구/출구
  r3  O2    .  .   .   .   B-1   .  C-1   .   .   .   .   O9     [A-3] = 2칸이 1자리
  r4 [A-3   .  .   .   .   B-2   .  C-2   .   .   .   .   D-3    A = 왼쪽 열(c0)
  r5  A-3]  .  .   .   .   O5    .  O7    .   .   .   .   D-4    B = 중앙 섬 좌(c5)
  r6  O3    .  .   .   .    .    .   .    .   .   .   .   O10    C = 중앙 섬 우(c7)
  r7  A-4   .  .   .   .    .    .   .    .   .   .   .    .     D = 오른쪽 열(c12)
  r8   .    .  .  OU   .    .    .   .   IN   .   .   .    .

열 배분(실측): c0<->c5 = 50cm, c5<->c7 = 20cm, c7<->c12 = 50cm, 전체 폭 120cm
```

**주차 구역 종류** (`SPOT1`~`SPOT4`, `map_data.SPOT_TYPE_NAME`)

| 종류 | 상수 | 자리 | 칸/자리 | UI 색 |
|---|---|---|---|---|
| 일반 | `SPOT1` | A-1, A-2, D-1~D-4 (6자리) | 1 | 회색 |
| 장애인 | `SPOT2` | A-4 (1자리) | 1 | 파랑 |
| 대형 | `SPOT3` | A-3 (1자리) | **2** | 노랑 |
| 전기차 | `SPOT4` | B-1, B-2, C-1, C-2 (4자리) | 1 | 초록 |

> **한 자리가 여러 칸을 차지할 수 있다.** 대형차는 차체가 길어 세로 2칸이 **1자리**다.
> 격자에 `SPOT3`가 2칸(r4, r5)으로 그려져 있어도 `A-3` 하나로 묶인다. 묶는 규칙은
> `map_data.SPOT_CELL_SPAN`(종류별 세로 칸 수)이 정하고, 자리의 실좌표는
> 묶인 칸들의 **가운데**가 된다. (A-3 → y = 78.8cm, 반높이 17.5cm)

**배정 우선순위** — `map_data.SPOT_PRIORITY`에 종류별로 **고정**해 둔다.

| 종류 | 순서 |
|---|---|
| 일반 | D-4 → D-3 → D-2 → D-1 → A-2 → A-1 |
| 장애인 | A-4 |
| 대형 | A-3 |
| 전기차 | C-2 → C-1 → B-1 → B-2 |

입구가 오른쪽 아래(r8,c8)이므로 **오른쪽 열을 아래에서 위로 채우고, 그다음 왼쪽 열**이다. 입구에서의 직선거리로 자동 정렬하지 않는 이유는 직선거리가 실제 주행거리와 다르기 때문이다(왼쪽 열은 직선으로 가까워 보여도 주차장을 가로질러야 한다). 목록에 없는 자리는 배정되지 않으므로 자리를 늘리면 이 표에도 적어야 하고, 배치를 바꿔 ID가 어긋나면 import 시점에 경고가 뜬다.

중앙 섬(전기차)은 **일방통행 순환 순서 그대로**다. 오른쪽 통로를 올라가며 C열을 아래(C-2)에서 위(C-1)로 지나치고, 윗줄을 돌아 왼쪽 통로로 내려오며 B열을 위(B-1)에서 아래(B-2)로 지나친다. 순서를 섞으면 지나친 자리로 되돌아가라는 안내가 되는데, 일방통행에서는 그럴 수 없다. → 2.1절

- 바깥 양쪽 열에 자리가 늘어서고, 가운데 두 섬 사이가 전부 도로인 **개방형 배치**
- 입구는 아래 오른쪽(r8,c8), 출구는 아래 왼쪽(r8,c3) → 안쪽을 돌아 왼쪽으로 빠지는 흐름
- **구역 ID는 `grid_map`에서 자동 생성된다.** 자리가 있는 열을 왼쪽부터 A, B, C, D로,
  각 열 안에서는 위에서부터 1, 2, 3... 으로 매긴다. 손으로 적어두지 않으므로
  `grid_map`만 고치면 `spot_map` / `coord_to_spot` / `spot_status` / 입출구 좌표가
  전부 따라온다. (`PILL_MARKER_ID`만 물리 정보라 수동)
- 배치 확인: `python logic/C02_lot_layout.py`

**실측 치수 (목업)**

| 항목 | 상태 | 값 | 유도 |
|---|---|---|---|
| 좌우 끝 기둥 간격 (c0 - c12) | 실측 | 120cm | `CELL_W_CM` = 120 / 12 = 10.0 |
| 섬 구간 (c0-c5 / c5-c7 / c7-c12) | 실측 | 50 / 20 / 50cm | 열 배분을 이 비율에 맞춤 |
| 세로 기둥 간격 (r0 - r3) | **미측정** | — | `CELL_H_CM` = 간격 / 3 |
| 현재 설정값 | | `CELL_W_CM` 10.0 / `CELL_H_CM` 17.5 | 세로는 아직 가정값 |

> **세로는 아직 실측 전이다.** 현재 값이면 기둥 1과 3 사이가 105cm여야 한다.
> 재서 다르면 `실측값 / 6`으로 `C02_lot_layout.CONFIG['CELL_H_CM']`을 고칠 것.
> 이 값이 틀리면 좌표 오차가 커지고 안내 거리가 전부 어긋난다.

> **거리 임계값은 이 규모에 맞춰져 있다.** 주차장을 키우거나 줄이면
> `C02.CELL_W/H_CM`뿐 아니라 `C00`의 `ARRIVAL_THRESHOLD_CM`,
> `C01`의 `VEHICLE_CLEARANCE_CM`·`REPLAN_TOLERANCE_CM`도 함께 조정해야 한다.
> 특히 `VEHICLE_CLEARANCE_CM`은 통로를 양쪽에서 깎으므로,
> `CELL_W_CM - 2 x VEHICLE_CLEARANCE_CM`이 0 이하가 되면 경로를 못 찾는다.

### 3.6 렌즈 왜곡은 좌표 변환보다 먼저다

픽셀↔cm 변환은 **직선을 직선으로만** 보낸다. 광각 렌즈가 담은 휘어진 화면에는
아무리 잘 맞춰도 한계가 있다. 배럴 왜곡을 바꿔가며 기둥 좌표의 오차를 잰 결과:

| 배럴 왜곡 | 기둥 평균 오차 | 기둥 최대 오차 |
|---|---|---|
| 없음 | 0.00cm | 0.00cm |
| 약함 | 0.66cm | 1.36cm |
| 강함 | 2.28cm | 7.73cm |

**평균만 보면 안 된다.** 평균 2.3cm는 기준(10cm)을 통과하지만 최대는 7.7cm로
10cm 칸의 3/4이다. 그 근처 자리는 통째로 어긋난다.

**왜곡이 남아 있어도 자리는 기둥에 붙는다.** 자리 좌표를 등록된 격자가 아니라
실제로 찍은 기둥에서 다시 계산하기 때문이다(`C02.build_spot_pixel_pos`). 격자에서
가져오는 것은 배치 정보(어느 기둥 사이에 어떤 자리가 있는가)뿐이다. 다만 이건
완화이지 해결이 아니다. 기둥에서 먼 곳은 여전히 휜다.

> **현재 파이프라인에는 렌즈 보정 단계가 없다.** 체스보드 캘리브레이션 모듈
> (`B04_lens_calib`)은 제거했고 `config/camera_calib.npz`만 남아 있다.
> 광각 렌즈로 바꿔 오차가 커지면 이 단계를 되살리고, 되살린 뒤에는 화소 위치가
> 통째로 달라지므로 기둥 보정을 반드시 다시 찍어야 한다.

### 3.7 카메라 해상도

> **캡처 해상도는 `1280x800`(16:10)이 기본이다.** (`B00_camera_input.DEFAULT_WIDTH/HEIGHT`)

조건이 두 개인데 서로 당긴다.

1. **주차장 전체가 화면에 들어와야 한다.** (반드시) 안 들어오면 기둥을 찍을 수 없어 보정 자체가 안 된다.
2. **학습 데이터와 가로세로비가 같으면 좋다.** (권장) YOLO는 입력을 비율을 지킨 채 정사각(`imgsz` 640)에 레터박스한다. 학습 데이터는 4:3이다.

실측에서 4:3(640x480)으로 내렸더니 카메라가 센서를 잘라 써서 주차장 좌우가 잘렸다.
그래서 1번이 이긴다. 4:3보다 넓으면서 4:3에 가장 가까운 16:10을 쓴다.
카메라가 이 값을 안 받아주면 `B00`이 `FALLBACK_SIZES`를 따라 16:9로 내려가고 로그에 남긴다.

**해상도 숫자 자체는 검출 성능과 거의 무관하다.** 어떤 해상도든 프레임 가로가
텐서 640px로 매핑되므로, 화각이 같으면 텐서에서 보이는 차 크기는 같다.
차를 크게 보이게 하려면 해상도가 아니라 `IMGSZ`를 올려야 한다.

| 위치 | 값 |
|---|---|
| `B00_camera_input.DEFAULT_WIDTH/HEIGHT` | 기본값. 인자를 안 주면 이 값 |
| `B01_car_detection.CONFIG` | B01 단독 실행용 |
| `B_main.CONFIG` / `C_main.CONFIG` | 통합 실행용 (E_main_final은 C_main 것을 씀) |

> **해상도를 바꾸면 기둥 보정을 다시 찍어야 한다.** 저장된 좌표가 이미지 픽셀이다. (3.4절)

> **`B01_car_detection.CONFIG['IMGSZ']`(640)는 이것과 무관하다.** YOLO의 추론
> 해상도로, 입력이 얼마든 내부에서 리사이즈한다. **화각에 영향을 주지 않는다.**
> `.engine`(TensorRT)은 빌드 시점에 입력 크기가 고정되므로 이 값을 바꾸면
> 매 프레임 `AssertionError`가 난다. 바꾸려면 엔진을 다시 export해야 한다.
> ```
> yolo export model=yolov8s.pt format=engine imgsz=1280
> ```

## 4. 이름 / 데이터 형식 규칙

| 대상 | 형식 | 예 | 비고 |
|---|---|---|---|
| 차량번호 (`car_id`) | **4자리 문자열** | `"1234"`, `"0828"` | **정수 아님.** 앞자리 0이 사라진다 |
| 주차 구역 (`spot_id`) | `"<구역><숫자>"` | `"A-1"`, `"B-3"` | 하이픈 포함, 대문자 |
| 추적 ID (`track_id`) | 정수 | `5` | 추적기가 발급. **재사용 안 됨** |
| 마커 ID (`marker_id`) | 정수 | `8` | |
| 좌표 | `(x, y)` 튜플 | `(90.0, 0.0)` | cm, float |
| 점유 상태 | `"empty"` / `"full"` | | 다른 문자열 금지 |

`track_id`와 `car_id`는 **다른 것**이다. 트랙이 끊겼다 다시 잡히면 같은 차량이라도 `track_id`는 새로 발급된다.

그래서 **하위 모듈은 `track_id`가 아니라 `car_id`를 키로 써야 한다.** (C00의 `world_history` / `routes` / `targets`가 모두 그렇게 되어 있다)

B02가 이 원칙을 세 겹으로 뒷받침한다. `track_id`는 바뀌어도 `car_id`는 물리적인 차를 계속 따라간다.

| 레이어 | 담당 | 움직임 필요? | 설정 |
|---|---|---|---|
| **주차 결합** | 이미 세워둔 차를 자리 근처 트랙에 묶는다 | 불필요 | `SINGLE_ACTIVE['PARKED_BIND_RADIUS_CM']` |
| **단일 활성 차량** | 움직이는 차 = 지금 안내 중인 차. ID가 바뀌면 즉시 재결합 | **필요** | `CONFIG['SINGLE_ACTIVE']` |
| **재바인딩(유령)** | 사라진 트랙의 마지막 위치를 남겨뒀다 새 ID에 승계 | 불필요 | `CONFIG['REBIND']` |

**운영 전제: 동시에 움직이는 차는 1대.** 차가 한 대씩 들어와 배정된 구역에 주차하고, 그다음 차가 들어온다. 이 제약이 어떤 추적 알고리즘보다 강한 단서이므로 B02는 이것을 1순위 규칙으로 쓴다.

**한 번호는 한 트랙.** 붙이는 통로가 셋이라 각자 '이미 임자가 있는 번호'를 걸러야 하는데,
셋 다 **살아 있는 트랙만** 봤다. `track_to_car`는 트랙이 사라져도 `lost_ttl`(약 2초)이
지나야 지워지므로, 그 사이 옆을 지나던 트랙이 자리 근처에 들어와 같은 번호를 받아갔고
원래 트랙이 같은 ID로 되살아나면 **화면에 같은 번호가 두 개** 떴다.

이제 번호를 붙이는 곳은 `_bind_car` 하나뿐이고, 붙이기 전에 그 번호를 쥔 다른 트랙을
살았든 죽었든 전부 떼어낸다. 어긋난 상태로 들어온 프레임은 `_drop_duplicate_car_ids`가
매 프레임 훑어 하나만 남긴다.

**주차를 마친 차는 출차까지 잠근다.** `parked_lock = {차량번호: Track ID}`.
그 차는 출차 정보가 올 때까지 제자리에 있으므로 번호가 옮겨 다닐 이유가 없다.

| 통로 | 주차 완료 차량에 대해 |
|---|---|
| 주차 결합 (`_bind_parked_cars`) | **유일한 통로.** 자리 좌표와 대조해서만 옮긴다 |
| 재바인딩(유령) | 막힌다. 거리만 맞으면 옆을 지나가는 차가 번호를 가져갔다 |
| 단일 활성 차량 | 원래도 다른 번호를 쥔 트랙은 후보에서 뺀다 |

잠금은 `release_car`(출차)와 `_sync_parked_state`(주차 목록에서 빠짐)에서 풀린다.
검출이 끊겨 **박스가 사라지는 것까지는 막지 않는다.** 자리 기록으로 점을 유지하는 것은
3번 구간(`_build_cars_on_map`)이 이미 하고 있고, 2번 카메라 화면에 없는 박스를 그리면
'검출이 되는지'를 화면으로 진단할 수 없게 된다.

### 4.1 유령 수명은 프레임레이트에 매여 있다

세 레이어의 분담은 이렇다. **움직이는 차는 단일 활성 차량 규칙이, 멈춘 채 새 ID로 돌아온 차는 유령이** 잡는다. 안내 중인 차가 끊긴 채 멈춰버리면 유령 말고는 번호를 되찾을 길이 없다.

그런데 두 시간 기준의 단위가 다르다.

| | 단위 | 9.5fps에서 |
|---|---|---|
| `lost_ttl` (= 추적기 `track_buffer`) — 트랙 결합을 버리는 시점 | **프레임** (60) | 6.3초 |
| `REBIND['MAX_GAP_SEC']` — 유령 수명 | **초** (3.0) | 3.0초 |

승계에는 **유령이 살아 있고** + **옛 결합이 정리되었을 것**이 둘 다 필요한데, 위 값이면 두 구간이 겹치지 않아 재바인딩이 **한 번도 돌지 않는다.** 30fps 기준(2초 < 3초)으로 잡아둔 값이 프레임레이트가 떨어지면서 조용히 뒤집힌 것이다.

그래서 유령 수명은 고정값이 아니라 **실측 프레임 간격에서 유도한다.**

```
_ghost_lifetime() = max(MAX_GAP_SEC, lost_ttl × 실측 프레임간격 + GHOST_MARGIN_SEC)
```

- 프레임 간격은 `CarMOT._tick_frame_interval()`이 지수이동평균으로 잰다. 설정에 적힌 fps를 믿지 않는 이유는 검출이 무거워 실제 처리 속도가 카메라 fps의 1/3까지 떨어지기 때문이다.
- 함께 고친 것: `_try_rebind`의 '임자 있는 번호' 판정은 **이번 프레임에 살아 있는 트랙이 쥔 것만** 센다. 죽은 트랙이 물고 있는 번호까지 세면 정작 승계해야 할 새 트랙이 걸러진다. (`_bind_parked_cars`에 이미 같은 처리가 들어가 있다)
- 안내 중인 차의 유령은 도달 상한을 따로 둔다(`MAX_REACH_ACTIVE_CM`). 전제상 오인 위험이 작은 반면, 상한이 좁으면 몇 초 끊긴 사이 이동한 거리에 걸려 안내가 통째로 끊긴다.

`python logic/B02_car_mot.py`의 **시나리오 5**가 이 관계를 가짜 시계로 직접 검사한다. `유령이 추적기보다 오래 사는가`가 FAIL이면 이 레이어는 죽어 있는 것이다.

### 4.2 안내를 끝내는 세 가지 길

| 사유 | 조건 | 결과 |
|---|---|---|
| 도착 | 목표 구역 `ARRIVAL_RADIUS_CM` 이내에 `ARRIVAL_HOLD_SEC` 이상 | 정상 주차 |
| 정지 안전장치 | `STUCK_RELEASE_SEC` 동안 반경 밖에서 정지 **+ 그 자리가 빈 주차구역 `STUCK_SPOT_RADIUS_CM` 이내** | E00이 위치로 오주차 판정 |
| 출차 | `release_car()` | 활성 해제 |

목표 좌표는 C_main이 `C00.get_target_world`를 `CarMOT.update(target_of=...)`로 넘겨서 전달한다.

**멈춰 있다 ≠ 주차했다.** 예전에는 시간만 보고 해제해서, 통로 한복판에 세워둔 차도 곧바로
'다른 곳에 주차 완료'로 처리됐다. 그 차의 안내가 끝나고 다음 차가 들어오는데 정작 통로는
막혀 있고, 관제 화면에는 "주차 자리를 파악하지 못했습니다"만 떴다.

그래서 조건을 하나 더 건다. 멈춘 자리가 **차를 댈 수 있는 빈 구역** 근처일 때만 주차로
인정하고, 그 밖에서 멈춘 것은 길에 선 것으로 보아 **안내를 유지한 채 계속 기다린다.**
빈 구역 목록은 C_main이 `free_spots_of`로 넘긴다. 주차를 마친 차가 차지한 자리만 빼고,
배정만 되고 오는 중인 자리는 남긴다. (그 자리는 실제로 비어 있다)

`STUCK_SPOT_RADIUS_CM`은 E00의 `MISPARK_MAX_DIST_CM`이 그대로 가져다 쓴다. 둘이 다르면
B02는 주차로 인정했는데 E00은 어느 자리인지 모르는 회색지대가 생긴다.

빈 구역 목록을 받지 못하면(단독 실행 등) 예전처럼 시간만으로 해제한다. 판단할 재료가
없는데 영영 안 풀리게 두면 다음 차가 막히기 때문이다.

> **정지 안전장치는 활성 차의 트랙이 살아 있을 때만 돈다.** 트랙이 없으면 카운트다운이 시작되지 않는다. 이건 의도한 것이다 — 안 보인다고 안내를 끊으면 다시 나타났을 때 이어갈 수 없다. 대신 위 세 레이어가 트랙을 되찾아 주고, 되찾은 뒤에 안전장치가 정상적으로 돈다.

## 5. 설정값을 어디에 둘 것인가

| 종류 | 위치 |
|---|---|
| 모듈 전용 파라미터 | 해당 모듈 파일 상단 `CONFIG` 딕셔너리 |
| 추적기 파라미터 | `config/ocsort.yaml` (사용 중) / `config/bytetrack.yaml` (비교용). ultralytics 내장 파일을 쓰지 않는다. 어떤 추적기를 쓸지는 yaml의 `tracker_type`이 결정 |
| 단일 활성 차량 / 주차 판정 반경 | `B02_car_mot.CONFIG['SINGLE_ACTIVE']` |
| 재바인딩 파라미터 | `B02_car_mot.CONFIG['REBIND']` |
| 주차장 지도 / 구역 목록 | `data/map_data.py`의 `grid_map` (나머지는 여기서 자동 생성) |
| 마커 ID 배치 | `data/map_data.py`의 `PILL_MARKER_ID` |
| 자리 배정 순서 | `data/map_data.py`의 `SPOT_PRIORITY` |
| 요금 | `data/car_data.py`의 `get_fee_config()` |
| 격자 칸 크기 (cm) | `C02_lot_layout.CONFIG` |

**시연 전에 만지는 차량 관련 설정은 `data/car_data.py` 한 곳에 모아두었다.**

| 설정 | 용도 |
|---|---|
| `car_types` | 번호판 → 차량 종류. 어느 종류의 구역으로 갈지 결정한다 |
| `INITIAL_PARKED` | 시작부터 세워둘 차량. 자리 상태 + 차량 정보 + 종류를 함께 채운다 |
| `TEST_PRESET_CAR_NUMBERS` | UART 없이 돌릴 때 순서대로 입차시킬 번호 |

`TEST_PRESET_CAR_NUMBERS`와 `INITIAL_PARKED`에 적은 번호는 `car_types`에도 등록해야 한다. 등록하지 않으면 전부 일반 차량으로 처리되어 대형/전기차 시나리오를 확인할 수 없다. (누락되면 import 시점에 경고가 뜬다)

`ENABLE_UART`가 켜져 있으면 `TEST_PRESET_CAR_NUMBERS`는 무시된다. 둘 다 넣으면 실제 입차와 테스트 번호가 뒤섞여 FIFO 순서가 어긋나기 때문이다.

규칙:

- **같은 값을 두 곳에 적지 않는다.** 통합 실행(`B_main`, `C_main`, `D00`)은 각 모듈의 `CONFIG`를 import해서 쓴다.
- 다른 모듈이 결정하는 값을 복사해 오지 않는다. 예: 매칭 정보 유지 시간(`lost_ttl`)은 `bytetrack.yaml`의 `track_buffer`에서 자동으로 가져온다.
- 모든 `CONFIG` 항목에는 **단위와 이유를 주석으로** 단다.

## 6. 실행 규칙

- 모든 모듈은 `python_code/`를 작업 디렉터리로 두고 실행한다.
  ```bash
  cd python_code && python logic/C_main.py
  ```
- 각 모듈은 `if __name__ == '__main__':` 블록에 **단독 테스트**를 갖는다. 가능하면 **카메라 없이** 돌아가게 만든다. (`B02`, `C01`은 합성 데이터로 검증 가능)
- 통합 실행의 최종 진입점은 **`E_main_final.py`**다. `B_main`/`C_main`/`D_main`은 그 아래 계층만 확인하는 용도.
  ```bash
  cd python_code && python logic/E_main_final.py
  ```
  기동 순서는 **UART → 카메라 → MOT → 화면** 4단계로 고정이다. UART를 먼저 띄우는 이유는
  카메라와 YOLO 로딩에 수 초가 걸리는데 그 사이 Zybo가 접속하면 거부되기 때문이다.
  Zybo 없이 확인하려면 `E_main_final.CONFIG['ENABLE_UART'] = False`로 두고 `/enqueue/1234`를 쓴다.
- 웹 서버 포트는 **5000** 고정. `B_main`, `C_main`, `D00`, `D_main`, `E_main_final`이 같은 포트를 쓰므로 **동시에 하나만** 띄운다.
  - VS Code의 포트 자동 전달이 `127.0.0.1:5000`을 선점하면 브라우저가 무한 로딩된다. VS Code "포트" 패널에서 5000을 제거할 것.
- `D00_ui_navi.py`는 **순수 렌더러**다. 단독 실행 진입점이 없고 `D_main` / `E_main_final`이
  `NavigationView` / `NavigationMapUI`를 가져다 쓴다.

### 6.1 실행 중에 쓰는 점검 경로

| 경로 | 하는 일 |
|---|---|
| `/status` | 추적/내비 상태 JSON. `tracks.detected`(YOLO가 찾은 수) vs `tracks.total`(트랙 수) |
| `/overlay` | 격자·자리·일방통행 화살표 오버레이 토글 |
| `/rawdet` | **YOLO 원본 박스 + 신뢰도** 토글. 아래 판별표 참고 |
| `/enqueue/<번호>` | UART 없이 입차 한 대 밀어넣기 |
| `/recalibrate` | 저장된 기둥 보정을 지우고 다시 찍기 |

**어떤 차만 박스가 안 뜰 때.** `B02.draw_tracks`는 트랙을 **전부** 그린다.
초록은 '번호가 매칭됐다'는 뜻일 뿐이고, **박스가 아예 없다는 것은 트랙이 없다는 뜻**이다.
`/rawdet`을 켜서 원인을 가른다.

| `/rawdet` 화면 | 원인 | 손볼 곳 |
|---|---|---|
| 얇은 박스도 없다 | YOLO가 그 차를 못 본다 | 학습 데이터에 그 차종을 넣고 재학습 |
| 얇은 박스에 `LOW` | 신뢰도가 새 트랙 임계값에 못 미침 | `config/ocsort.yaml`의 `new_track_thresh` |
| 박스는 있는데 주황(WAIT) | 트랙은 있는데 번호 매칭 실패 | `B02`의 `PARKED_BIND_RADIUS_CM`, 기둥 보정 |

> 1·3번 구간의 "주차완료" 목록은 **`cars_info`를 읽는다. 카메라와 무관하다.**
> `data/car_data.py`의 `INITIAL_PARKED`로 미리 세워둔 차는 영상에서 한 번도 검출되지
> 않아도 목록과 배치도에는 계속 '주차완료'로 뜬다. 두 화면이 어긋나 보이는 것은
> 버그가 아니라 출처가 다른 것이다.

## 7. 최종 화면 (E 계층)

`E_main_final.py`를 실행하면 나오는 관제 화면. 위에 1번 가로 띠, 아래를 2·3·4번이 3등분한다.

```
+------------------------------------------------------------------+
| 1) Zybo 수신 & 차량번호 FIFO                                        |
|   [수신] -push-> [FIFO 대기열 front→back] -pop-> [안내 중] [주차완료]  |
+--------------------+-------------------+-------------------------+
| 2) 주차장 CCTV       | 3) 주차장 상태      | 4) 실시간 주차 안내        |
+--------------------+-------------------+-------------------------+
```

| 구간 | 내용 | 그리는 주체 |
|---|---|---|
| **1** | 수신 → FIFO 대기열 → 안내 중 → 주차 완료 (가로 흐름) | 브라우저 (`/ui_state`) |
| **2** | 카메라 원본 + 검출/추적/배치 오버레이 | 서버 MJPEG (`/video_feed`) |
| **3** | 자리 현황 + 배정 자리 깜빡임 + 일방통행 화살표 + **안내 경로(파란 선)** | 브라우저 (`/lot_layout`, `/ui_state`) |
| **4** | 차량 시점 실시간 안내 (`D00.NavigationView`) | 서버 MJPEG (`/nav_feed`) |

**영상 위 상태 글자는 기본으로 꺼져 있다.** FPS / Tracks / FIFO / Map / 단계별 소요시간은
2번 구간 왼쪽 아래 **[디버그]** 버튼(또는 `/debug`)으로 켠다. 같은 값을 화면 아래 정보줄이
한글로 이미 보여주는 데다, 큰 글자가 왼쪽 위 차량을 가려서 시연 화면에 늘 떠 있을 이유가 없다.

**영상 위 트랙 목록에는 안내 중인 차만 띄운다.** 주차를 마친 차까지 전부 띄우면 목록이
화면 절반을 덮는다. 세워둔 차의 위치는 3번 격자의 점과 영상의 초록 박스가 이미 보여준다.

**일방통행 화살표는 화면에 그리지 않는다.** (`C_main.CONFIG['DRAW_ONE_WAY_ARROWS']` = False,
3번 격자에서도 제거) 목업 바닥에 실물 화살표가 붙어 있어 2번 CCTV에 그대로 보이므로,
화면에 또 그리면 같은 정보가 두 겹이 되고 안내 경로와 겹쳐 읽기 어려워진다.

**1번을 가로 띠로 올린 이유.** 이 구간이 보여주는 것은 '한 대의 차가 수신에서 안내,
주차 완료까지 지나가는 흐름'이다. `B02.CarNumberFIFO`가 실제로 하는 일(뒤로 쌓고 앞에서
꺼낸다)을 왼쪽에서 오른쪽으로 그대로 늘어놓는다. **대기열을 숫자 하나('대기 3대')로
줄이면 어느 차가 다음 차례인지가 화면에서 사라진다.** 맨 앞 카드가 `front`이고,
다음에 움직이는 차가 잡히면 그 번호가 나간다.

**1·3번을 OpenCV로 그리지 않는 이유.** 두 구간은 한글 안내문이 핵심인데 `cv2.putText`는
한글을 못 그린다. (`D00`의 `MANEUVER_LABEL`이 전부 영문인 것도 같은 이유) 영상인 2·4번만
MJPEG로 넣고 나머지는 브라우저가 그린다. 깜빡임도 CSS 애니메이션이 프레임 재생성보다 싸다.

**3번과 4번은 같은 경로를 그린다.** 둘 다 `pick_my_vehicle`로 같은 차를 고르고, C00이
계획한 같은 `route_cm`을 쓴다. 4번은 그것을 차 기준으로 돌려 원근을 입힐 뿐이다.
4번만 있을 때는 화면이 차를 따라 돌고 원근이 걸려 있어 안내가 일방통행을 지키는지
눈으로 판정할 수가 없었다. 3번 격자는 바닥 화살표와 같은 평면·같은 방향이라 겹쳐 보면
바로 읽힌다. 역주행 구간을 물고 나온 경로는 **붉은 선**으로 그린다.

**4번은 안내가 끝나도 마지막 모습을 붙들고 있다.** 주차가 끝나면 그 차의 목표가 지워지는데,
예전에는 그 순간 '번호가 붙은 아무 차'로 넘어가 화면이 엉뚱한 주차 차량과 그 자리로 튀었다.
추적이 잠깐 끊겨도 마찬가지였다. 지금은 갈아타지 않고 마지막 위치에 멈춰 있으며, 왼쪽 아래
알약에 `last seen`이 붙는다. 다음 차가 안내를 시작하면 그때 넘어간다. (`pick_my_vehicle`)

**2번 영상의 노란 직선과 좌표 글자는 [디버그]를 켤 때만 나온다.** 그 직선은 통로도 일방통행도
무시한 직선이라 주차 구역과 다른 차를 관통해 지나간다. 안내를 그렇게 하라는 뜻으로 읽히지만
실제 경로가 아니다. 진짜 경로는 3번 격자와 4번 화면이 그린다.
(`C_main.CONFIG['DRAW_NAVIGATION']`)

**계획된 경로가 없을 때 4번이 그리는 회색 점선은 경로가 아니다.** 목적지 방향만 가리키는
직선이라 통로도 일방통행도 지키지 않는다. 예전에는 이것도 같은 파란 띠로 그려서, 주차
구역을 관통하고 역주행으로 보이는 선이 계획기가 낸 것으로 오해됐다.

### 7.1 주차 완료 / 오주차 판정

`B02`는 두 경우에 안내를 끝내고 둘 다 `A01.mark_parked`를 부른다. 콜백만으로는 구분이 안 된다.

| B02의 종료 사유 | 실제 의미 |
|---|---|
| 목표 구역 반경 안에서 `ARRIVAL_HOLD_SEC` 유지 | 제대로 주차 |
| `STUCK_RELEASE_SEC` 동안 반경 밖에서 정지 | 엉뚱한 곳에 주차 |

그래서 `E00.ParkingWatcher`가 **차량의 마지막 실좌표를 매 tick 캐시**해 두었다가,
`parked`가 `False → True`로 바뀌는 순간 배정된 자리와 비교한다.
전이를 감지한 시점에는 이미 `latest_nav`에서 그 차가 빠져 있을 수 있어 캐시가 필요하다.

- 배정 자리에서 `MISPARK_TOLERANCE_CM` 이내 → `지정 자리 주차 완료`
- 벗어났고 `MISPARK_MAX_DIST_CM` 안에 다른 자리가 있음 → `운전자가 다른 위치에 주차하였습니다`
  + `A01.relocate_car`가 기록을 실제 자리로 옮긴다 (원래 자리는 비우고 실제 자리를 채움)
- 벗어났는데 어느 자리로도 보기 어려움 → 자리를 **옮기지 않고** 경고만 띄운다

두 임계값은 모두 `B02_CONFIG['SINGLE_ACTIVE']['ARRIVAL_RADIUS_CM']`을 그대로 쓴다.
따로 두면 도착도 오주차도 아닌 회색지대가 생긴다. **B02의 도착 반경을 바꾸면 여기도 같이 바뀐다.**

> 이 목업은 폭이 120cm뿐이라 자리가 촘촘하다. 통로 한가운데(60,60)에서도 가장 가까운
> 자리까지 5cm다. `MISPARK_MAX_DIST_CM`를 키우면 통로에 멈춘 차까지 아무 자리에나 배정한다.

### 7.2 주의

- `ParkingWatcher.prime()`을 감시 시작 전에 반드시 부른다. 없으면 기동 직후 첫 tick에서
  미리 세워둔 차(`car_data.INITIAL_PARKED`)가 전부 "방금 주차함"으로 잡혀 안내가 쏟아진다.
- `A00_uart_rx.add_rx_listener()`는 **수신 서버를 띄우기 전에** 등록한다. 첫 패킷을 놓치지 않기 위해서.
- 실제 자리가 이미 다른 차로 차 있으면 `relocate_car`는 옮기지 않고 실패를 돌려준다.
  한 자리에 두 대를 기록하면 이후 출차와 배정이 전부 엉킨다.

## 8. 코드 작성 규칙

- 주석·docstring·로그는 **한국어**.
- 로그는 대괄호 태그로 시작한다: `[INFO]` `[경고]` `[ERROR]` `[TEST]` `[FIFO]` `[매칭]` `[소실]` `[안내]` `[입차 완료]`
- docstring에는 **Args / Returns**를 적는다. 특히 딕셔너리를 반환하면 키를 전부 나열한다.
- `.pyc` / `__pycache__`는 커밋하지 않는다.
- 커밋 메시지는 `feat:` `fix:` `perf:` `docs:` 접두어 + 한국어 요약.

## 9. 알려진 제약 / 미해결 (건드리기 전에 읽을 것)

1. **학습 데이터에 없는 차종은 트랙이 아예 안 생긴다.**
   `B01`은 직접 촬영해 라벨링한 1클래스 데이터셋으로 파인튜닝한 모델을 쓴다.
   데이터에 없는 차체(예: 흰 대형차)는 검출되지 않고, 검출이 없으면 트랙도 없다.
   박스가 안 보일 때 원인을 가르려면 `/rawdet`을 켤 것. (6.1절)

2. **거리 임계값이 목업 규모에 묶여 있다.**
   폭 120cm 목업 기준으로 도착 반경 8cm, 주차 결합 15cm 등을 잡았다.
   실제 주차장에서는 `C02.CELL_W/H_CM`과 함께 전부 다시 잡아야 한다.

3. **동시에 움직이는 차는 1대라는 전제에 기대고 있다.**
   이 전제가 번호 매칭의 1순위 규칙이다. 두 대가 동시에 움직이면 활성 차량
   결합이 어긋난다. 전제를 풀려면 외형 특징 기반 재식별이 필요하다.

4. **트랙을 완전히 놓치면 차량번호가 회수되지 않는다.**
   재바인딩 레이어가 대부분 잡아주지만(4.1절), 유령 수명을 넘겨 놓친 경우는
   FIFO 앞에 번호를 되돌리는 경로가 없다.

5. **경로 길이는 맨해튼이라 실제 최단이 아니다.**
   차선 인력(2.1절)과 4방향 제한으로 '통로를 따라 가로/세로로만' 가는 경로가 되었다.
   대신 대각선으로 질러갈 수 있는 구간도 돌아가므로 거리는 조금 길다. 이 목업에서는
   통로가 좁아 어차피 대각선이 의미 없지만, 넓은 주차장에서는 다시 볼 값이다.

6. **보정 화면은 카메라를 직접 읽지 않는다.**
   `/snapshot`은 `PipelineRunner`가 받아둔 최신 원본을 그대로 내준다. 예전에는 카메라를
   다시 `read()`했는데, 처리 스레드도 같은 카메라를 최대 속도로 읽고 있어서 둘이 같은
   프레임 커서(`B00`의 `_last_read_seq`)를 놓고 다퉜다. 그 결과 보정 사진이 안 뜨거나
   처리 스레드의 프레임을 가로챘다. **`/calibrate`에 들어갔는데 사진이 안 나오면**
   `register_map_routes`에 `runner`가 넘어갔는지부터 확인할 것.

7. **기둥 보정은 한 번 찍으면 고정된다.**
   카메라가 움직이면 모든 위치가 어긋난다. 카메라를 옮겼으면 `/recalibrate` 후
   다시 찍을 것. 해상도가 바뀐 경우는 자동으로 거부된다. (3.4절)

8. **렌즈 왜곡 보정 단계가 없다.**
   광각 렌즈로 바꾸면 좌표 오차가 커진다. (3.6절)
