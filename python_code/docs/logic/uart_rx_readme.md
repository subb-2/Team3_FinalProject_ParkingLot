# 00_uart_rx 모듈 명세서 (README)

## 통신 양식 (UART RX)

Zybo 보드로부터 데이터를 수신할 때의 규칙과 데이터 포맷. 
수신 데이터는 총 **16비트(2바이트)**의 순수 바이너리(Binary) 데이터로 구성되며, 이를 4비트씩 쪼개어 파싱함으로써 최종적으로 **4자리의 숫자(예: "1234")**를 수신.

### 데이터 패킷 구조 (Data Packet Structure)

수신되는 2바이트는 각각 8비트이며, 8비트는 다시 절반(4비트)씩 쪼개어 숫자의 한 자릿수를 의미함.

**수신 순서 및 비트 할당:**

**4자리의 숫자 예시 : 1234**

1. **첫 번째 바이트 (Byte 1)**
   - 상위 4비트 (1-1): 첫 번째 자릿수 (예: "1")
   - 하위 4비트 (1-2): 두 번째 자릿수 (예: "2")
   - 구조: `_ _ _ _ ..(1) / _ _ _ _ ..(2)`

2. **두 번째 바이트 (Byte 2)**
   - 상위 4비트 (2-1): 세 번째 자릿수 (예: "3")
   - 하위 4비트 (2-2): 네 번째 자릿수 (예: "4")
   - 구조: `_ _ _ _ ..(3) / _ _ _ _ ..(4)`

### 작동 원리 (코드 기준)
- 파이썬의 `ser.read(2)`를 통해 한 번에 2바이트(16비트)를 수신.
- 비트 연산(`>> 4` 시프트 연산 및 `& 0x0F` 마스킹 연산)을 통해 각각 4등분으로 파싱.
- 최종적으로 4개의 숫자를 문자열로 합쳐(예: "1234") 메인 로직으로 전송.

## 보드마다 다른 바이트 순서 (실측)

위 설명은 '한 바이트 안에서 상위 4비트가 앞자리'라는 부분만 두 보드가 같다.
**두 바이트 중 어느 쪽을 먼저 보내는지는 보드마다 다르다.** 실물 번호판
8935로 확인한 값이다.

| 역할 | 보내는 순서 | 8935를 보내면 | `BYTE_ORDER` |
|------|-------------|---------------|--------------|
| 입차 | 앞 두 자리 먼저 | `0x89 0x35` | `high_first` |
| 출차 | 뒤 두 자리 먼저 | `0x35 0x89` | `low_first`  |

순서를 잘못 잡으면 앞뒤 두 자리가 뒤집힌 번호가 된다. (8935 → 3589)
입차에서는 등록되지 않은 번호가 되어 조용히 일반 차량으로 처리되고,
출차에서는 그 번호의 입차 기록이 없으므로 거부된다. 시연 번호판이
1111, 2222처럼 앞뒤가 같으면 뒤집혀도 같은 값이 나와 드러나지 않는다.

값은 `A00_uart_rx.BYTE_ORDER`에 역할별로 적혀 있다. 펌웨어에서 순서를
바꾸면 그 역할만 여기서 되돌리면 된다.

## 포트와 역할

입차는 5001, 출차는 5002 포트로 받는다. 다만 포트가 곧 역할은 아니다.

- **이미 자리에 세워져 있는 차의 번호가 입차 포트로 들어오면 출차로 처리한다.**
  나가려고 움직이는 차를 입구 카메라가 다시 읽어 보내는 경우다. 그대로
  입차로 처리하면 "이미 주차 중입니다"로 거부되고 정작 출차는 어디에도
  뜨지 않는다. (`A00_uart_rx.resolve_packet`)
- 두 보드가 같은 포트로 붙어도 IP가 다르면 둘 다 받는다. 역할을 IP에
  못박으려면 `ROLE_RESOLVE['ROLE_BY_IP']`에 적는다.
- 이 재분류가 싫으면 `ROLE_RESOLVE['KNOWN_CAR_IS_EXIT'] = False`로 끈다.
